# Tally design: durable facts before derived views

Tally demonstrates a financial-record correctness boundary on synthetic data. It does not move money, integrate a bank or provide financial advice. The hard part is preserving the same journal, balances and decision explanation when requests race, acknowledgements disappear, rules change, or a projection is rebuilt.

Money crosses JSON as bounded integer strings and is computed with BigInt or exact Postgres NUMERIC, never binary floating point. Each journal has one currency and distinct accounts; its signed lines must balance. Accounts can explicitly disallow negative balances. Cross-currency conversion is outside this version.

A database-owned posting function takes a transaction-scoped advisory lock for the ledger chain. It checks immutable idempotency, locks affected account rows in stable order, appends the event and lines, updates projections, and returns only after transaction commit. Database constraints and deferred triggers independently reject unbalanced/incomplete events and mismatched currencies. Application credentials cannot update or delete journal facts or directly change balances. A global chain gives a simple total commit order at the cost of serialized posting throughput. Sequence gaps from aborted transactions are permitted.

The chain binds the previous digest to the exact stored event text. Replay verifies hashes, IDs, ordered sequence values and request bindings, then reconstructs balances independently. Projection repair takes the same ledger lock, compares the reconstruction with stored balances, and rebuilds the derived state transactionally. Hashes detect modification relative to a trusted chain head; a database administrator who can rewrite the entire chain is outside the trust boundary. This is not external notarization or tamper-proof storage.

Decision rules are immutable content-addressed snapshots. Each request names a version and persists its validated input and deterministic result. Duplicate request IDs return the original decision; changed inputs or versions conflict. A response deadline is a latency budget, not hard real-time scheduling. Work that loses an acknowledgement may still commit, so callers retry the same request ID. Admission capacity is retained until database work actually ends. Benchmarks include HTTP transport and durable database writes, count failures, and report the full latency samples.

Reconciliation uses exact amount/currency constraints plus a bounded date window and normalized descriptor similarity. A candidate must be unambiguous in both directions; a ledger row cannot be claimed twice. Batches retain input snapshots, matches, unresolved exceptions and audited manual resolutions. Review uses an expected row version and database uniqueness, so racing reviewers cannot silently assign the same ledger row. Match precision and recall include deliberately unmatched and noisy cases; abstention is visible.

Descriptor enrichment uses a synthetic catalog with content versions and a bounded version-keyed cache. Similarity is not a calibrated probability. Synthetic market/merchant feeds preserve event timestamps and immutable point identities; monitoring distinguishes missing IDs, stale data, outliers and future timestamps rather than treating recent ingestion as fresh source data.

The NestJS API has provisioned operator credentials, hashed/revocable sessions, CSRF-protected writes and a separate machine token. Logs contain request traces, status and timing rather than payloads or credentials. Metrics and the React console show committed state. The local stack runs real Postgres. Public hosting must distinguish an actual persistent service from a recording/evidence page; no stateless in-memory ledger will be presented as durable hosting.
